# CTS500

The [CTS500](https://www.alibaba.com/product-detail/Mini-Climbing-Training-Scale-CTS500-Aluminum_1601637814595.html),
sold as the “Jlyscales CTS500” by
[Hunan Jinlian Cloud Information Technology Co., Ltd.](https://www.huaying-scales.com/), appears to be a China-made copy
of the Tindeq Progressor.

## Basic usage

```ts
import { CTS500 } from "@hangtime/grip-connect"

const device = new CTS500()
device.notify((data) => console.log(data.current))

await device.connect(
  async () => {
    console.log("Battery:", await device.battery())
    console.log("Model:", await device.model())
    console.log("Serial:", await device.serial())
    await device.stream(5000)
    device.disconnect()
  },
  (err) => console.error(err),
)
```

## Methods

CTS500 supports all [shared methods](/devices/#shared-methods) (connect, disconnect, isConnected, notify, active, read,
write, download). See [Device interface](/api/device-interface) for details.

### Device-specific

| Method                    | Returns                        | Description                               |
| ------------------------- | ------------------------------ | ----------------------------------------- |
| `battery()`               | `Promise<string \| undefined>` | Battery voltage.                          |
| `firmware()`              | `Promise<string \| undefined>` | Firmware version.                         |
| `firmwareUart()`          | `Promise<string \| undefined>` | Raw UART firmware payload as hex.         |
| `hardware()`              | `Promise<string \| undefined>` | Hardware version.                         |
| `manufacturer()`          | `Promise<string \| undefined>` | Manufacturer info.                        |
| `model()`                 | `Promise<string \| undefined>` | Model number.                             |
| `serial()`                | `Promise<string \| undefined>` | Serial number.                            |
| `software()`              | `Promise<string \| undefined>` | Software version.                         |
| `stream(duration?)`       | `Promise<void>`                | Start automatic weight uploads.           |
| `stop()`                  | `Promise<void>`                | Stop automatic weight uploads.            |
| `temperature()`           | `Promise<string \| undefined>` | Temperature in Celsius.                   |
| `weight()`                | `Promise<number \| undefined>` | Read the current weight in kilograms.     |
| `zero()`                  | `Promise<void>`                | Update the hardware zero point.           |
| `powerOnReset(enabled)`   | `Promise<void>`                | Toggle reset-to-zero on power-up.         |
| `peakMode(enabled?)`      | `Promise<void>`                | Toggle peak hold mode.                    |
| `setBaudRate(baudRate)`   | `Promise<void>`                | Configure the UART baud rate.             |
| `setSamplingRate(rateHz)` | `Promise<void>`                | Configure the A/D sampling rate in hertz. |

`firmware()` reads the Firmware Revision String from the BLE Device Information service (`0x180a`). `firmwareUart()`
sends the `GET_FIRMWARE_VERSION` (`0xA4`) command over the transparent UART service. It returns the raw response payload
as uppercase hex, for example `"20 3A 96"`. The encoding is unknown, so the method does not decode the bytes. `serial()`
returns the serial number when the device has the serial characteristic. It returns `undefined` when the device does not
have it.

## Command acknowledgments

Firmware 2.1.3 does not echo a command with a 6-byte frame. It answers with a typed 7-byte response instead:
`05 80 <opcode> <p0> <p1> <p2> <checksum>`. For example, `05 AB` (stop) receives `05 80 AB 00 00 00 30` as the answer.
The client accepts the typed response or the 6-byte echo. Therefore `stop()`, `zero()`, `peakMode()`, `powerOnReset()`
and `tare()` all resolve on this hardware. Earlier releases waited for the echo only. As a result, `stream(duration)`
appeared to fail at the end, because its internal `stop()` timed out after the device had already answered.

Some commands send no answer frame. For example, start measuring `05 AA` sends weight frames only. The client accepts
the next weight frame as the answer.

::: warning Changing the baud rate desynchronizes the link

`setBaudRate()` changes the MCU UART speed. The transparent Bluetooth module keeps its previous speed. When the two
speeds differ, the link stops working. The link stays broken until you re-flash the device. Leave the default (`38400`)
unchanged unless you can re-flash the device afterwards.

:::

## Troubleshooting: connected but no data

A CTS500 with a MY-BT102 module can connect, resolve its services, and answer writes while the UART bridge to the MCU is
dead. The device looks healthy, but every command then times out.

- Make sure that the wiring between the module and the MCU is correct.
- Make sure that the module baud rate matches the MCU. The default is `38400`.
- Software cannot fix this failure. When the bridge does not pass bytes, no client-side change will help.

## Commands that are deliberately not exposed

The firmware accepts several parameter and calibration commands. This client does not wrap them. They change persistent
device state, and the protocol has no read command for them. There is no `GET_RANGE`, `GET_DIVISION`, or
`GET_CALIBRATION`. Software therefore cannot make sure that a write is correct, and it cannot restore the previous
value.

| Command                             | Opcode         | Reason                                                                                |
| ----------------------------------- | -------------- | ------------------------------------------------------------------------------------- |
| Set range or capacity               | `0x81`         | Changes the load-cell scaling. The payload presets are not documented.                |
| Set division                        | `0x82`         | Changes the resolution and the rounding. The payload presets are not documented.      |
| Set calibration reference weights   | `0x83`, `0x84` | These values are the first step of a calibration run.                                 |
| Run the first or second calibration | `0xA1`, `0xA2` | Overwrites the calibration table. A repair needs known reference weights.             |
| No-load calibration                 | `0xA7`         | Rewrites the zero baseline.                                                           |
| Set baud rate                       | `0xC0`         | Can permanently break the link between the module and the MCU. See the warning above. |

The client also does not wrap weight and temperature alarm output (`0xD1` to `0xD4`). Alarm frames mix with the weight
stream and corrupt a measurement.

When you need these commands, write the frames yourself with the shared `write` method. A wrong calibration value leaves
the scale reporting incorrect weights until it is calibrated again with known weights.
